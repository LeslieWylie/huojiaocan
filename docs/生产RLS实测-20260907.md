# 活教参生产数据库账号隔离实测

## 项目确认

2026-09-07，管理后台项目仍名为 Life_k_line。通过该项目存在活教参三张业务表、已上线的专用回归草稿 ID，确认其与当前产品数据对应。此前因项目名称而未能确认的阻碍已解除。没有读取其他业务内容或任何实际密钥字段。

## 实际执行

在生产 Supabase 数据库执行 `supabase/tests/account-isolation-rollback.sql`，结果：

```json
{"mode":"database_roles_not_browser_sessions","checks_passed":39,"fixtures_rolled_back":true}
```

脚本创建两名临时身份及各自的草稿、模拟密钥记录、私人文档权限记录，切换到 authenticated 角色并设置各自的用户身份声明。每个用户、每张表检查：

1. 能读到自己的测试记录；
2. 读不到对方的测试记录；
3. 修改对方记录影响行数为0；
4. 删除对方记录影响行数为0；
5. 将自己的记录归属改为对方被策略拒绝；
6. 对自己的记录执行不改变归属的更新成功。

以上共36项；匿名身份访问三张表的私人测试记录均被拒绝或返回0行，合计39项。

所有测试写入在异常子事务中回滚，随后检查临时用户及三表记录均不存在。脚本没有持久修改策略、正式草稿或密钥，没有发起模型调用，也没有创建可登录的长期测试账号。任一断言失败会作为数据库错误返回，不用固定成功文案掩盖失败。

## 验证边界

- 三张表的RLS开关与用户归属策略已读取确认，且上述行为在生产数据库实际执行成功，不再只是本地mock证据。
- 这是数据库角色与身份声明层的隔离验证，不是两个真实浏览器登录会话，也不是PostgREST/JWT签名验证。
- 未覆盖私人PDF二进制下载路径、密钥解密和生成调用、INSERT伪造归属及所有其他业务表；不能据此宣称全产品安全验收完成。
- 前一轮的本地双账号浏览器流程、接口所有者约束、刷新竞态验证仍作为各自层次的证据，不能与本次数据库验证混为一个完整公网双账号流程。

## 运行注意

仅由已授权的数据库管理员在确认目标项目后执行。脚本使用随机UUID，不携带真实凭据。生产只需运行SQL验证，不需重新部署前端。
