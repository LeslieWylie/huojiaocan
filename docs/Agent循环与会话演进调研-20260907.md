## 四、当前实现的真实能力与缺口

### 已有
- pi-retrieval-agent.js 确实 new Agent 并运行工具循环，不是单次模板调用。
- 最多两次搜索、两次阅读，循环有时间与工具计数上限。
- pageindex-reading-context.js 在明确篇目下取得目录候选，发放本轮 sectionRef；读取原页时核对文档与物理页。
- 原页读取共享四页尝试预算；重复读取会推进至未读邻页，不应简单把同节点二次读取判为无效重复。
- ai-orchestrator.js 已有最多三轮结构化生成/审校，临时失败重试受剩余时间约束。
- api/index.js 的 ownedDraftAskContext 从当前账号所属草稿恢复历史和篇目身份。
- 前端已有生成完成但保存失败时的“仅重试保存”路径。

### 缺口
1. 检索 Agent 每次以空 messages 建立，只把近期历史放入当前请求。它保留问答语义，但不等于恢复上一次工具执行位置。
2. 模型回复 READY/INSUFFICIENT 的文字并不是服务端检索完成契约；当前返回仍由 evidence/coverage 与后续生成判断。
3. 检索扩展 catch 保留已有依据，但无法从结果明确区分正常结束、超时、工具失败或无新增依据。
4. 目录候选一次取得并截至24项。现有路径适合已知篇目，不是任意目录层级的动态探索工具。
5. 检索后进入独立生成修订；若审校发现缺少某个原段落，没有统一的“针对缺口回到原页”闭环。
6. 已发送对话持久化与执行中检查点是不同能力。当前路径未接入可恢复的 Agent run 记录。
7. 仅靠前端 busy 不能承担跨页面、跨实例的同轮请求去重。

这些判断限定在本轮核对的问答、检索、阅读与生成模块，不声称扫描了全部生产部署。

## 五、建议的目标模型

沿用产品语言，内部区分：
- teachingSession：当前用户的一份备课草稿，拥有固定篇目、条件、已确认内容。
- turn：教师提交的一轮问题，使用 clientRequestId 去重。
- run：一次执行尝试，绑定 owner、draftId、draftVersion、connectionId 与材料版本。
- checkpoint：已完成阶段的必要输入输出、预算余额、事件序号、结果引用与状态。

建议状态：
queued → retrieving → composing → checking → ready_to_save → saved。
分支：needs_input / needs_evidence / interrupted / failed。
模型检查通过只表示 ready_to_save，不等于教师确认。
HTTP 断开不直接判定 failed，须查询运行记录；存储成功才显示已保存。

存储先做决策验证：草稿 JSON 可以保存最终结果与摘要，不能无条件承载每秒进度写入。
若实现跨实例租约、追加事件、幂等登记，可能需要新的运行表或独立持久执行服务；这超出此前“不新增表/接口”的约束，需明确调整，不悄悄塞入草稿 JSON。

## 六、改造顺序

### A. 可解释的有界循环（先做）
- 增加结构化 stopReason：证据就绪、依据不足、时间耗尽、额度耗尽、工具失败、模型失败。
- 完成条件由代码检查：真实材料覆盖、任务所需原文是否读过、结果结构有效。
- 工具参数错误给模型可纠正 observation；不把授权拒绝当临时网络故障重试。
- 只有检索无新增依据且没有新的合法阅读动作时才停止空转。
- 引文纠错必须核对原文，不能仅以三类文档各有一条命中判定足够。
- 保持既有预算先建立基线；不预设多调用必然更好。

### B. 循环中的定向补读
- 审校输出结构化缺口类型，不要求展示内部思维过程。
- 只有缺材料类型能触发额外补读；纯表达问题不重复搜索。
- 补读占用同一总预算，最多一次回跳，然后定向修订；不足则向教师说明限制。
- 每个材料结果绑定版本、文档和物理页；不跨账号复用引用权限。

### C. 可恢复 session
- 提交前持久登记 requestId，重复点击返回同轮状态而不是重复付费调用。
- 同一草稿一次活跃执行；跨实例采用带到期时间的租约和版本校验。
- 保存 ready_to_save 输出，再写正式草稿；写入失败只重试保存。
- 页面刷新按 runId 取回状态，完整结果不依赖原页面继续存活。
- 连接 ID 固定到本轮；退出、换账号、撤销连接后重新验证，不能静默改用其他付费连接。
- 外部模型调用结果未知时，不承诺 exactly-once，不盲重放；显示结果待确认。
- 读取工具可以在校验版本后恢复；写入、分享等副作用必须单独幂等。

### D. 更自然的协作
- 在执行时允许“补充下一轮”，明确是排队，不隐式插入正在执行的问题。
- 教师选择“改当前要求”时显式取消/重开；在可靠取消和运行持久化前不启用 steering。
- 用 Pi 生命周期事件形成教师可读事件；不透传原始 tool args、模型思考或密钥。
- 需要澄清时问一个必要问题；缺教材、版本不一致不能假装靠多问模型解决。

## 七、验证与质量比较

本轮实际执行：
node --test serverless/pi-retrieval-agent.test.js serverless/pageindex-reading-context.test.js src/conversation-recovery.test.js
54项通过。它们是现有代码基线测试，不是新能力验收，也不含付费模型验证。

下一批新增用例：
1. 模型提前 READY 但缺原文：不能标记已核验。
2. 同节点继续读下一页允许；重复空结果不无限循环。
3. 审校缺原文只回跳一次；共享预算不重置。
4. 超时/工具失败保留已取得依据，停止原因准确。
5. 同 requestId 并发提交只有一个逻辑执行；跨实例接管检查租约。
6. 模型已返回而保存失败：恢复后模型调用计数不增加。
7. 刷新/掉线/重新登录后恢复同轮；账号B不能恢复账号A运行。
8. 排队问题按序执行，取消和课时调整不改变篇目。
9. 旧材料版本的 checkpoint 不直接用于新的引用绑定。

沿用四篇课文×备课/纠错/追问调整共12例，对比现行版本。
记录原文正确性、有效新增依据、完成/补材料率、教师修改量、真实耗时与调用成本。
不得用回答变长或模型自报“更准确”替代评测。

## OpenMAIC 复用决策（2026-09-07）

已核对 THU-MAIC/OpenMAIC 的 main@64621ad，上游为 MIT 许可证。本轮直接引入其已发布的
`@openmaic/generation@0.3.6`，使用 `withGenerationRetry` 与 `parseJsonResponse`，替代本项目对模型重试和
JSON 缺陷修复的自建实现。主项目仍保留自己的教材依据校验、顶层对象限制、共享请求截止时间和
最多一次重试；不沿用 OpenMAIC 面向课堂生成的默认五次重试。

OpenMAIC 的持久 Agent Session 是下一阶段最有价值的直接复用候选，它已提供租约、心跳、事件序列、取消、
中断工具结果修复和恢复规则。但 `@openmaic/storage` 的可靠实现依赖直连 PostgreSQL 交易和六张会话表；当前生产仅有
Supabase REST 访问边界。在未建立可交易的数据库连接与 RLS 迁移前，不把浏览器缓存包装成跨实例恢复，也不复制一份不具备
租约语义的简化版。
